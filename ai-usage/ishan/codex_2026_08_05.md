> The error I got from OpenRouter was upstream idle timeout exceeed, code 504 from openrotuer like the body

That means OpenRouter, or an upstream provider behind OpenRouter, accepted the request but the provider did not produce a response before their idle timeout.

`504 upstream idle timeout exceeded` is not your Postgres/Redis/SSE. It’s the model/provider side timing out.

What it implies:
- your request reached OpenRouter
- OpenRouter routed it upstream
- the upstream model/provider stayed idle too long
- OpenRouter returned `504`

Why it happens more with plan generation:
- full plan prompt/schema is heavier
- free Nvidia models can be overloaded
- many users testing can hit capacity/queueing
- structured JSON schema generation can be slow

Best fixes:
- Retry `504` with backoff.
- Lower worker concurrency so fewer OpenRouter calls happen at once.
- Use a more reliable paid model for plan generation.
- Reduce prompt/schema size if possible.
- Keep timeout reasonable, but increasing timeout may not help if OpenRouter’s upstream has its own idle timeout.

For now, treat `504` as retryable. Your code currently returns `null` on non-OK and then fails. Better behavior would be retry for `408`, `429`, `500`, `502`, `503`, `504`, `524`, `529`, then fail cleanly if all attempts fail.

Right now plan generation asks one model call to do everything:
- user summary
- calories/macros
- meal plan

That is a big structured-output request, especially for free models. Splitting can reduce 504s/no-content failures.

Good split for initial plan:

1. Nutrition call
   - calories/macros
   - meal frequency
   - one sample meal
   - target summary sentence

2. Workout schedule call
   - weekly schedule only
   - exercises, sets, reps, equipment
   - respects available days/equipment/injuries/session length

3. Optional final validation/repair call
   - checks combined JSON against constraints
   - or skip this and rely on Zod + deterministic checks

Good split for sync/adapt plan:

1. Workout adaptation call only
   - you already mostly do this
   - keep nutrition unchanged
   - return only `weekly_schedule` and `adaptive_notes`

So the biggest win is initial plan generation: split nutrition and workouts.

Tradeoffs:
- More OpenRouter calls per user.
- But each call is smaller, faster, and less likely to hit upstream idle timeout.
- You can retry only the failed piece.
- Easier logs: “nutrition failed” vs “workout failed.”
